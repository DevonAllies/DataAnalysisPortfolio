Excel for capturing data, not analysing it

Why spreadsheets make a risky place to analyse data, and how to set one up so the data going in is clean

Data management
Excel
R
Why Excel is a poor tool for data analysis (no record of the steps, silent conversions, easy invisible mistakes), with published examples, and how to use it well for data capture instead: layout rules, data validation with drop-down lists, ranges, dates and ID checks, its limits, and checking the data again in R. Includes an example workbook to download and adapt.
Author

Devon Allies

Published

November 25, 2026

Almost every research group I’ve worked in keeps its data in Excel, and for good reason: it’s on every computer, everyone knows the basics, and typing into a grid is the easiest way to record what comes off a bench or out of a clinic. The trouble starts when the same spreadsheet is also used to sort, calculate, summarise and plot.

This article makes one argument in two halves. Excel is a reasonable place to capture data and a risky place to analyse it. The first half explains why, with published examples. The second shows how to set up a spreadsheet so the data going in is as clean as possible, with an example workbook to download and adapt.

Part 1: why not analyse data in Excel

There’s no record of what you did

An analysis in Excel is a series of clicks: a sort here, a filter there, a formula dragged down a column, a chart from a selection. None of it is written down. The file keeps the result, not the steps, so nobody can check how a number was produced or repeat it with corrected data. That includes you, six months later, when a reviewer asks.

A script in R or Python is the opposite: every step is written out, in order, and running it again on new data repeats the whole analysis exactly. That’s the main reason analysis belongs in code, and the reason this site’s tutorials use it.

It changes your data without asking

Excel guesses what you meant as you type or open a file, and some of its guesses are wrong in ways that are easy to miss:

  • Gene names become dates. Gene symbols such as SEPT1 or MARCH1 look like dates to Excel, which converts them to dates when a list is typed, pasted or opened. A scan of leading genomics journals found the errors in about one in five papers with supplementary Excel gene lists (Ziemann, Eren and El-Osta, 2016). A follow-up of papers from 2014 to 2020 found them in 30.9% (3,436 of 11,117), and found the problem had kept growing after it was first reported (Abeysooriya et al., 2021). In the end the HUGO Gene Nomenclature Committee renamed every human gene symbol that converted to a date: SEPT1 is now SEPTIN1 and MARCH1 is now MARCHF1 (Bruford et al., 2020).
  • Leading zeros disappear. An ID or code such as 00731 is read as the number 731.
  • Long numbers are rounded. Excel keeps 15 significant digits (Microsoft, 2025a), so longer numbers, such as some barcodes and sample identifiers, lose their last digits.
  • Dates are read in the wrong order. Whether 03/04/2019 means 3 April or 4 March depends on the computer’s settings, so the same file can give different dates on two computers.

Small mistakes are easy to make and hard to see

  • Sorting one column breaks the rows. Select a single column and sort it, and its values move away from the rest of their rows. Every row is now wrong, and nothing on screen says so.
  • A formula range stops short. A total or average that covers rows 2 to 50 silently ignores row 51. In one well-known case, an influential economics paper on public debt and growth was found on re-analysis to have a spreadsheet coding error that “entirely excludes five countries, Australia, Austria, Belgium, Canada, and Denmark, from the analysis” (Herndon, Ash and Pollin, 2013; published as Herndon, Ash and Pollin, 2014).
  • Hidden rows and filters. A filtered sheet still looks complete, and copying or summing it can include or leave out rows you didn’t intend.
  • Pasted values over formulas. A cell that should be calculated can be overwritten with a fixed number, and looks exactly the same.

Size limits can lose data

A worksheet holds at most 1,048,576 rows (Microsoft, 2025a), and the older .xls format far fewer. In October 2020, Public Health England reported that 15,841 COVID-19 cases had been left out of the UK’s daily figures because some files “exceeded the maximum file size” (Public Health England, 2020). Reporting at the time attributed this to the old XLS format, which can hold only about 65,000 rows (Kelion, 2020).

Colour and formatting carry meaning nothing else can read

Highlighting a cell in yellow to mean “check this”, or bold to mean “repeat sample”, records information that only a person looking at the screen can see. It’s lost the moment the data is read into any other software, exported to CSV, or opened by someone who doesn’t know the code.

None of this means Excel is bad software. It means a spreadsheet is designed for looking at and editing a grid of values, not for keeping a reliable record of an analysis.

Part 2: capturing data well

Data has to be entered somewhere, and for many studies a spreadsheet is the practical choice. The goal then is to make it as hard as possible for a bad value to get in, and as easy as possible for the next step, the analysis in code, to read the file.

Layout first

Broman and Woo’s short paper Data Organization in Spreadsheets (Broman and Woo, 2018) is the standard reference. Its main rules:

  • One row per record and one column per variable, with a single header row and nothing above it.
  • One value per cell. Not 120/80 for blood pressure, not positive (repeat).
  • Consistent values. One spelling for each category, one code for each meaning.
  • Dates as YYYY-MM-DD (ISO 8601), which can’t be read in the wrong order.
  • Blank for missing. Not 999, NA, - or a colour.
  • No merged cells, no calculations, no colour as data in the data sheet.
  • A data dictionary: a separate sheet saying what every column means, its type, allowed values and units.

Then data validation

Excel’s data validation (Data → Data Validation) checks each value as it’s typed, and can refuse it. It’s the single most useful thing you can add to a data-capture sheet, because it stops errors at the moment they happen instead of leaving them to be found later.

The messy files in my tutorial series show what happens without it. They’re simulated, and made messy on purpose to match what real study files look like, but every problem in them is a common one:

Twenty-one ways of writing five smear grades (NEG, 0, negative, +2, 1 +, two plus, …), 49 spellings of 11 clinics, and dates typed as 20/08/2018, 15-02-2020, 17/07/17 and 14 July 2017. Cleaning these up takes most of Tutorial 3. A drop-down list and a date rule would have prevented nearly all of it.

The example workbook

To show the techniques together, I built an example data-capture workbook for the same study. It’s an example to learn from and adapt, not a template to fill in: open it, click around, look at how each rule is set up, then design your own for your study’s variables.

Download the example workbook (.xlsx)

It has four sheets:

  • Read me: what the workbook demonstrates and how each rule was set up.
  • Data: one row per participant, with a rule on every column and five simulated example rows.
  • Lists: the allowed values for each drop-down, in one place. Change a list here and every drop-down that uses it follows.
  • Data dictionary: each column’s meaning, type, allowed values and units, and the rule for missing values.

The rules on the Data sheet, and what each demonstrates:

Three features make validation much more useful:

  • Input messages. Each column shows a short note when a cell is selected (“Type the date as YYYY-MM-DD…”), so the person entering data knows what’s expected before they type.
  • Error-alert styles. Stop refuses a value outright, for impossible values. Warning asks “Continue?”, for values that are unusual but possible, such as a weight of 210 kg. Information only informs. Choosing the right one for each column keeps the sheet strict without being obstructive.
  • Protection. The Data sheet is protected (with no password, in the example) so the header row can’t be renamed or deleted by accident, while the data cells stay editable. Review → Unprotect Sheet removes it.

What validation can’t do

Validation is worth setting up, but it has limits that matter:

  • Pasted values skip it. Microsoft’s own documentation is explicit: validation is “designed to show messages and prevent invalid entries only when users type data directly in a cell. When data is copied or filled, the messages do not appear” (Microsoft, 2025b). Copying a block of values from another file, which is how a lot of data arrives, bypasses every rule without warning.
  • Existing data isn’t checked. Adding a rule to a column doesn’t test what’s already there. Data → Data Validation → Circle Invalid Data highlights every cell that breaks a rule, pasted ones included: run it before a file is shared or analysed.
  • Rules can be removed, by anyone who can edit the sheet (protection helps).
  • Plausible but wrong values get through. A real date that’s the wrong date, or a weight of 65 kg typed as 56, passes every rule.

So check again in code

Because of those limits, the analysis step should check the data again when it reads the file. The same rules take a few lines in R, and they run every time, on every row, however the values got in. Here they are applied to the example workbook and to the messy tutorial file:

Show the code: the workbook’s rules, written in R 
allowed <- list(
  sex = c("Female", "Male"),
  hiv = c("Negative", "Positive"),
  smear = c("Negative", "Scanty", "1+", "2+", "3+")
)

check <- function(df, id, sex, hiv, smear, age) {
  c(
    `ID not SP + 5 digits` = sum(!grepl("^SP[0-9]{5}$", df[[id]])),
    `Duplicate ID` = sum(duplicated(df[[id]])),
    `Sex not in list` = sum(!df[[sex]] %in% allowed$sex),
    `HIV status not in list` = sum(!df[[hiv]] %in% allowed$hiv),
    `Smear grade not in list` = sum(!df[[smear]] %in% allowed$smear),
    `Age outside 0-120` = sum(!between(as.numeric(df[[age]]), 0, 120), na.rm = TRUE)
  )
}

example <- read_excel("bal-capture-example.xlsx", sheet = "Data")

tibble(
  Rule = names(check(example, "pt_id", "sex", "hiv_status", "smear_grade", "age")),
  `Example workbook` = check(example, "pt_id", "sex", "hiv_status", "smear_grade", "age"),
  `Messy tutorial file` = check(messy, "Pt_ID", "Sex", "HIV_Status", "Smear_Grade", "Age")
) |>
  kbl() |>
  kable_styling(bootstrap_options = c("striped", "condensed"), full_width = FALSE, position = "left")

The example rows pass every check. The messy file breaks these six rules 562 times across its 502 rows, mostly categories spelled in ways the lists would have refused; its ages are all plausible, which a range rule alone can’t confirm are correct. In a real study, the checks would run on the full data each time it’s updated, and anything they flag goes back to the person who entered it. Tutorial 3 works through this kind of audit in detail.

When a spreadsheet isn’t the right tool

For clinical studies, purpose-built data-capture systems do everything above and more. REDCap (Harris et al., 2009), widely used in academic clinical research, builds data-entry forms with validation on every field, keeps an audit trail of every change (who, what and when), controls who can see and edit what, and exports clean data straight to R or Python. Mobile tools such as KoBoToolbox do similar jobs for field surveys. If your institution offers one of these, it’s usually a better choice than a shared spreadsheet, especially for anything involving participants.

If you don’t code

Not everyone who analyses data writes R or Python, and the point of this article isn’t that they must. It’s that the analysis should happen somewhere that keeps a record of what was done. Some point-and-click programs do that far better than Excel:

  • jamovi (The jamovi project, 2026) and JASP (JASP Team, 2026) are free and open source. Each saves the data, the analyses and their settings together, and updates the results when the data change, so the file itself records what was done. jamovi is built on R and can show “the exact R syntax behind every analysis”, which makes it a good step towards scripting. Both read data laid out as in this article (one row per record, one column per variable) directly.
  • GraphPad Prism (GraphPad Software, 2026b) is a commercial program that needs a licence, and it’s the standard in many immunology and cell-biology labs. Analyses and graphs stay linked to their data table and update automatically when the data are edited, which is a large improvement on formulas scattered across a spreadsheet. Most of its analyses, though, expect their own table layouts: in a Column table, for example, “each column defines one group” (GraphPad Software, 2026a). Data captured one row per record usually has to be rearranged before it goes in, and that rearranging (and any filtering or excluding before it) is a step that leaves no record.

Whichever you use, the rule from Part 2 still holds. Keep the validated capture workbook as the single source, copy data out of it into the analysis program rather than editing it there, and note any rows you leave out and why.

In short

Keep the spreadsheet as the place data goes in, set it up so bad values are hard to enter, and leave every step after that to code, or to a program such as jamovi, that records what it did.
